# Агрополия — принятые архитектурные поправки к ФТЗ

**Статус:** принято к учёту в проектировании  
**Дата:** 2026-10-01  
**Основание:** обсуждение архитектуры ФТЗ v1.0 от 23.09.2026  
**Назначение:** зафиксировать согласованные изменения и уточнения к разделам 6 и 9 ФТЗ до выпуска следующей редакции основного документа.

> До включения этих формулировок в следующую версию ФТЗ данный документ имеет приоритет как рабочее архитектурное соглашение проекта по перечисленным ниже вопросам.

---

## 1. Архитектура MVP: модульный монолит

### Изменение к §9.3 и NFR-MNT-01

Для MVP базовой серверной архитектурой является **модульный монолит**, а не набор независимо развёртываемых микросервисов.

Доменные границы, указанные в §9.3 ФТЗ, сохраняются как логические модули с явными контрактами, но не требуют отдельных deployment unit.

Рекомендуемая начальная структура backend:

```text
backend/
  auth/
  organizations/
  fields/
  catalog/
  scouting/
  community/
  tasks/
  market/
  compliance/
  notifications/
  integrations/
  shared/
```

Допускаются отдельные процессы одного приложения для API, фоновых workers, бота, scheduler и специализированных gateway-компонентов.

Выделение модуля в самостоятельный сервис допускается только при наличии подтверждённой причины, например:

- независимое масштабирование;
- отдельный SLA;
- существенно отличающийся профиль нагрузки;
- отдельный жизненный цикл релизов;
- изоляция по безопасности;
- технологическая необходимость.

Такое выделение оформляется ADR.

Формулировку NFR-MNT-01 следует трактовать как требование к **архитектурным модулям с явными контрактами**, а не как обязательное требование к микросервисному развёртыванию.

---

## 2. Версии клиентского стека

### Изменение к §9.2

ФТЗ не должно фиксировать устаревающие major/minor версии frontend-библиотек без необходимости совместимости.

Целевая формулировка:

> React + TypeScript + Vite; используются актуальные поддерживаемые stable-версии на момент начала реализации. Конкретные версии фиксируются lockfile и при необходимости ADR.

Версии, влияющие на минимально поддерживаемые ОС, native API или обратную совместимость, фиксируются отдельно.

---

## 3. Capacitor и обязательный технический spike

### Уточнение к NFR-PLT-01

Одна кодовая база означает единый продуктовый и UI-слой, но не предполагает идентичную реализацию platform-specific функций.

До основной реализации должен быть выполнен технический spike для проверки на целевых Android/iOS устройствах:

- background sync;
- push;
- SQLite;
- MapLibre и offline tiles;
- загрузка и докачка медиа;
- камера;
- GPS;
- защищённое хранение;
- восстановление фоновых операций после OS kill.

Результаты spike фиксируются ADR/технической заметкой.

---

## 4. Абстракция локального хранилища клиента

### Уточнение к §9.2 и §9.5

IndexedDB/Dexie для web/PWA и SQLite для Android/iOS рассматриваются как две реализации общего persistence abstraction.

Прямые platform checks в бизнес-логике не допускаются.

Целевая схема:

```text
Domain / application layer
        |
Repository interfaces
        |
Local persistence abstraction
        |
   +----+----+
   |         |
SQLite    IndexedDB
native      web
```

Outbox и sync engine работают через этот абстрактный слой.

Для web/PWA отдельно определяется модель хранения чувствительных данных с учётом того, что возможности защиты IndexedDB отличаются от native SQLite.

## 5. Offline sync: отказ от LWW по клиентскому времени

### Изменение к FR-OFFLINE-03 и §9.5

Правило `last write wins` по `updated_at` устройства не используется как универсальный механизм разрешения конфликтов.

Каждая offline-операция, изменяющая версионируемую сущность, должна передавать ожидаемую серверную версию:

```json
{
  "client_op_id": "...",
  "entity_id": "...",
  "base_version": 7,
  "operation": "...",
  "payload": {}
}
```

Сервер применяет optimistic concurrency:

- если `base_version == current_version` — операция применяется и версия увеличивается;
- если версии различаются — применяется доменная merge policy либо возвращается `CONFLICT`;
- клиентское время не является источником истины для порядка изменений.

LWW допускается только как явно заданная политика для отдельных безопасных атрибутов и должно быть описано в соответствующем доменном модуле.

## 6. Асинхронная архитектура: NATS JetStream вместо Celery/Arq в MVP

### Изменение к §9.2, §9.6

Для MVP **NATS JetStream является единой инфраструктурой асинхронной доставки**:

1. доменных и интеграционных событий;
2. фоновых команд/jobs.

Celery и Arq в MVP не используются.

Redis не используется как task broker. Его назначение в MVP:

- cache;
- rate limiting;
- краткоживущие distributed locks — только там, где они обоснованы.

### 6.1. События

Событие фиксирует уже произошедший факт и может иметь несколько независимых потребителей.

Примеры:

```text
events.observation.confirmed
events.question.answered
events.task.done
events.meteo.hazard.detected
```

Consumers обязаны быть идемпотентными.

### 6.2. Фоновые команды

Фоновая команда означает необходимость выполнить асинхронную работу.

Примеры:

```text
jobs.media.make_preview
jobs.report.generate
jobs.ml.classify
jobs.notification.send
```

Workers реализуются как Python-процессы — NATS consumers.

API и workers могут собираться из одного Docker image с разными entrypoint:

```text
api
outbox-worker
event-worker
job-worker
scheduler
```

### 6.3. Scheduled jobs и бизнес-таймеры

NATS не является источником истины для отложенного бизнес-состояния.

Дата следующего действия хранится в PostgreSQL, например:

```text
Question.next_escalation_at
Notification.scheduled_for
BeeNotice.scheduled_for
```

Scheduler выбирает наступившие записи из PostgreSQL и публикует соответствующую команду в NATS.

Это обеспечивает восстановление после рестарта и делает бизнес-таймеры частью доменного состояния.

## 7. Transactional outbox / inbox на backend

### Дополнение к §9.5–§9.6 и NFR-REL-04

Изменение доменного состояния и регистрация события выполняются в одной транзакции PostgreSQL.

Целевая схема:

```text
PostgreSQL transaction
  |- domain changes
  '- outbox_event
          |
          v
   outbox publisher
          |
          v
     NATS JetStream
```

Требования:

- событие не публикуется напрямую из request handler до фиксации транзакции;
- outbox publisher повторяет публикацию до подтверждённой доставки;
- consumers используют inbox/idempotency mechanism по `event_id`;
- повторная доставка события не меняет результат обработки.

Особенно критично для цепочек:

- Treatment -> BeeNotice;
- RFQ -> Lead;
- Hazard -> Notification;
- billing;
- analytics.

---

## 8. PostgreSQL: одна база, схемы по bounded context

### Изменение к §9.2

Для MVP используется один PostgreSQL cluster/database.

Доменные области разделяются логическими схемами, например:

```text
auth.*
org.*
field.*
scouting.*
community.*
market.*
tasks.*
compliance.*
```

Отдельная БД на каждый логический сервис в MVP не требуется.

Разделение схем сохраняет архитектурные границы и упрощает последующее выделение модуля в самостоятельный сервис при необходимости.

---

## 9. Аналитическое хранилище — заменяемый компонент

### Изменение к §9.2 и §10

Приложение и аналитический ingestion не должны зависеть от ClickHouse как от обязательного компонента MVP.

Вводится интерфейс/адаптер аналитического storage.

**MVP:** конкретное хранилище выбирается отдельно исходя из доступной инфраструктуры.

**Backlog:** внедрение ClickHouse как целевого аналитического хранилища при подтверждённой необходимости.

Схемы событий EV-* и ingestion contract не должны зависеть от конкретного storage engine.

---

## 10. Kubernetes — backlog

### Изменение к §9.2

Kubernetes не является обязательной частью MVP.

Deployment unit — Docker image/container.

Для dev допускается Docker Compose.

Production-схема выбирается исходя из инфраструктуры РИВЦ/Ростелекома. Kubernetes может быть внедрён позднее без изменения прикладной архитектуры и относится в backlog.

При проектировании сервисов нельзя создавать зависимость application layer от Kubernetes-specific механизмов.

---

## 11. RPO/RTO и резервное копирование

### Изменение к NFR-REL-02

Требование `RPO <= 15 минут` должно обеспечиваться механизмами непрерывного восстановления, а не только ежедневными backup.

Для PostgreSQL:

- continuous WAL archiving / PITR;
- RPO <= 15 минут;
- регулярные full/base backup;
- периодическая автоматизированная проверка backup;
- restore drill не реже одного раза в месяц.

Для объектного хранилища и других stateful-компонентов RPO/RTO задаются отдельно и должны быть технически обеспечены выбранной инфраструктурой.

---

## 12. Шифрование данных at rest и управление ключами

### Дополнение к NFR-SEC-01, NFR-SEC-05, NFR-SEC-08

Помимо TLS и шифрования backup, требования безопасности должны явно включать защиту данных at rest.

### 12.1. PostgreSQL

Данные production PostgreSQL должны храниться на зашифрованных томах/дисках либо в инфраструктуре, предоставляющей эквивалентное managed encryption at rest.

Ключи шифрования не хранятся вместе с данными в открытом виде.

### 12.2. Object storage

Приватные медиа, отчёты и экспортируемые документы должны храниться с server-side encryption или эквивалентным механизмом.

Public preview не должен становиться источником исходных EXIF/геоданных.

### 12.3. Backup

Backup PostgreSQL и object storage шифруются отдельно от production storage.

Доступ к backup и ключам восстановления должен быть ограничен отдельными ролями.

### 12.4. Управление ключами

Должны быть определены:

- владелец ключей;
- механизм хранения KMS/Vault/корпоративный аналог;
- rotation policy;
- процедура отзыва/замены;
- разделение доступа к ключам и данным;
- процедура восстановления ключей при DR.

### 12.5. Mobile

Токены и ключевой материал хранятся в Keystore/Keychain.

SQLite на native-устройствах должен использовать доступный механизм шифрования, если устройство и выбранная библиотека его поддерживают.

Для web/PWA отдельно фиксируется набор данных, которые разрешено сохранять в IndexedDB.

## 13. Разделение operational logs и security/audit logs

### Изменение к NFR-SEC-09 и DM-42

Определяются два класса журналов.

### Operational logs

- не содержат ПДн;
- не содержат точные контуры и координаты;
- используют псевдонимные идентификаторы;
- предназначены для диагностики, telemetry и эксплуатации.

### Security / Audit logs

Могут содержать минимально необходимый набор идентификаторов и технических данных, включая IP, если это требуется для аудита безопасности.

Для audit logs должны быть отдельно определены:

- ACL;
- retention;
- защита от изменения/удаления;
- аудит чтения;
- порядок экспорта для расследований.

Operational logs и AuditLog не считаются одним и тем же типом данных.

## 14. Tenant isolation

### Дополнение к NFR-SEC-04 и §9.7

Межорганизационная изоляция является отдельным security invariant системы.

Требования:

- `org_id` для защищённых операций определяется из авторизованного контекста, а не принимается как доверенное поле payload;
- каждый запрос к tenant-owned resource проверяет membership/role/resource ownership;
- попытка доступа к ресурсу другой организации не должна раскрывать наличие объекта;
- обязательны automated tests на horizontal privilege escalation;
- публичные и приватные DTO физически разделены;
- применение PostgreSQL Row Level Security для наиболее чувствительных таблиц рассматривается как defense-in-depth и фиксируется отдельным ADR.

---

## 15. Idempotency retention

### Изменение к FR-OFFLINE-02 и DM-43

Результат обработки `client_op_id` хранится **30 дней по умолчанию**.

Значение 30 дней не хардкодится и хранится в серверной конфигурации:

```text
sync.idempotency_retention_days = 30
```

Для операций с критичными бизнес-последствиями одной временной дедупликации недостаточно. Дополнительно должны применяться доменные invariant/unique constraints для предотвращения дублей, в частности для:

- Treatment;
- BillingEvent;
- BeeNotice;
- RFQ/Lead;
- иных финансовых или регуляторных операций.

---

## 16. Стратегия тестирования: risk-oriented coverage

### Изменение к NFR-MNT-02 и §12.2

Метрика unit coverage сохраняется как вспомогательный hygiene metric, но не является основным критерием достаточности тестирования.

Обязательный набор тестов строится вокруг архитектурных и доменных invariants.

Приоритетные зоны:

- tenant isolation;
- privacy DTO;
- offline sync conflicts;
- state machines;
- idempotency и event redelivery;
- transactional outbox/inbox;
- BeeNotice / регуляторные сроки;
- pesticide/catalog rules;
- billing;
- permissions / RBAC;
- миграции API и БД;
- восстановление после частичного отказа.

Критические invariants должны иметь явную трассировку к FR/NFR и автоматизированным тестам.

---

## 17. Серверная политика версий мобильного клиента

### Дополнение к NFR-PLT и API-конвенциям §9.4

Backend хранит серверную конфигурацию поддерживаемых версий клиента отдельно по платформам.

Минимальный набор:

```json
{
  "android": {
    "latest_version": "1.4.3",
    "minimum_supported_version": "1.3.0",
    "recommended_version": "1.4.3"
  },
  "ios": {
    "latest_version": "1.4.2",
    "minimum_supported_version": "1.2.0",
    "recommended_version": "1.4.2"
  }
}
```

Семантика:

- `latest_version` — последняя опубликованная версия;
- `recommended_version` — версия, на которую следует предложить обновиться;
- `minimum_supported_version` — минимальная версия, с которой backend гарантирует работу.

Поведение клиента:

- версия ниже `recommended_version`, но не ниже minimum — мягкое предложение обновления;
- версия ниже `minimum_supported_version` — обязательное обновление.

Клиент передаёт backend версию и платформу в стандартизованном client context/header.

Повышение `minimum_supported_version` выполняется только после проверки доли активных клиентов и наличия опубликованной версии во всех обязательных store.

Изменение feature flags и runtime-конфигурации не требует нового mobile release.

# НА ОБСУЖДЕНИЕ

## Географическая обфускация публичных координат

Текущая формулировка FR-PRIV-02 со случайным смещением centroid на 1–3 км требует отдельного privacy review.

Проблемы для обсуждения:

1. Если случайное смещение пересчитывается на каждый запрос, несколько наблюдений позволяют статистически приблизиться к исходной координате.
2. Стабильное смещение защищает от усреднения, но может сохранять корреляцию публикаций одного поля.
3. В малонаселённой сельской местности комбинация «культура + район + расстояние + дата» сама по себе может позволять идентифицировать хозяйство.

Варианты для ADR:

- стабильное псевдослучайное смещение по publication/field + secret;
- coarse spatial cell (H3/geohash);
- округление/агрегация до населённого пункта/района;
- разные уровни точности для разных типов публикаций.

До принятия ADR правило FR-PRIV-02 остаётся действующим, но его конкретная реализация не считается окончательно утверждённой.

# Не включённые изменения

Следующие обсуждавшиеся уточнения сознательно **не принимаются как поправки к ФТЗ на данном этапе**:

- детализация SLO по отдельным capabilities;
- переработка NFR-PERF-02 по профилям нагрузки;
- разделение push latency на provider/device delivery;
- формализация сетевого профиля для upload NFR;
- reference device для performance NFR.

Они остаются без изменений относительно ФТЗ v1.0.
